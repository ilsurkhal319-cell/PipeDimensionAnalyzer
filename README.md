# Расчёт длины трубопроводов по изометриям с использованием ИИ

## Быстрый запуск MVP

Текущая версия реализует минимальный AI-first pipeline: каждая страница PDF рендерится через
PyMuPDF, отправляется мультимодальной модели со Structured Output, после чего Python проверяет
структуру, складывает подтверждённые размеры и формирует разметку.

Установка в активированное виртуальное окружение:

```bash
python -m pip install openai pydantic pymupdf pytest ruff
```

Ключ задаётся только через окружение:

```bash
export OPENAI_API_KEY="ваш_ключ"
export OPENAI_BASE_URL="https://api.vsegpt.ru/v1"
export OPENAI_MODEL="vis-openai/gpt-5-mini"
```

Сначала следует проверить отдельный учебный пример:

```bash
python analyze.py "/home/ilsur/Downloads/03_Пример_расчета_длины.pdf" \
  --output output/example
```

Ожидаемая программная сумма учебного примера — `4306 мм`.

После успешной проверки можно обработать 10 листов:

```bash
python analyze.py "/home/ilsur/Downloads/02_Изометрии_10_листов.pdf" \
  --output output/sheets
```

Результаты:

- `results.csv` — длины, формулы и статусы;
- `results.json` — полный структурированный ответ по страницам;
- `metrics.json` — фактические токены и время;
- `annotated.pdf` — разметка включённых и исключённых размеров.

Тест арифметики на эталонном примере:

```bash
pytest -q
```

Стоимость добавляется в `metrics.json`, если перед запуском заданы актуальные тарифы:

```bash
export OPENAI_INPUT_USD_PER_MTOK="..."
export OPENAI_OUTPUT_USD_PER_MTOK="..."
```

## Что требуется получить

Программа должна:

1. Принимать PDF с изометрическими чертежами.
2. Обрабатывать каждый лист отдельно.
3. Определять обозначение линии.
4. Находить линейные размеры основной трассы и ответвлений.
5. Учитывать каждый физический участок один раз.
6. Исключать вложенные и позиционные размеры.
7. Отмечать неоднозначные участки для ручной проверки.
8. Выполнять суммирование программно, а не силами LLM.
9. Формировать CSV или XLSX с результатами.
10. Формировать размеченный PDF, на котором видны учтённые, исключённые и спорные размеры.
11. Собирать статистику времени, числа запросов к ИИ и стоимости обработки.

## Главная сложность

Задача не сводится к OCR и сложению всех найденных чисел.

Для каждого числового размера необходимо определить:

- относится ли он к длине трубы;
- к какому участку трассы он относится;
- является ли участок основной трассой или ответвлением;
- не входит ли этот размер в более длинный размер;
- не был ли данный физический участок уже учтён;
- не является ли число координатой, отметкой, диаметром, номером позиции или служебным обозначением.

В учебном примере результат равен `4306 мм`:

```text
60 + 1950 + 650 + 840 + 522 + 250 + 34 = 4306 мм
```

Размеры `916` и `300` не прибавляются, поскольку задают положения элементов внутри уже учтённых участков.

## Принцип решения

Используется гибридный подход:

```text
PDF
  ↓
Извлечение текста и векторной геометрии
  ↓
Поиск кандидатов размеров и размерных линий
  ↓
Интерпретация связей мультимодальной моделью
  ↓
Построение графа трубопровода
  ↓
Детерминированные проверки
  ↓
Программное суммирование
  ↓
XLSX/CSV + размеченный PDF + метрики
```

ИИ используется для распознавания и семантической интерпретации чертежа. Итоговые арифметические операции, проверка структуры данных и формирование отчёта выполняются обычным Python-кодом.

Если результат нельзя подтвердить, система должна вернуть статус `review`, а не выдумывать длину.

## Почему сначала нужно разбирать PDF как векторный документ

Предоставленные PDF содержат извлекаемый текст и векторные линии. Поэтому не следует сразу превращать все страницы в изображения и отправлять их в OCR.

Предпочтительный порядок:

1. Извлечь встроенный текст вместе с координатами.
2. Извлечь векторные линии и штрихи.
3. Найти числовые кандидаты и размерные линии.
4. Использовать OCR только для фрагментов, которые не удалось разобрать напрямую.
5. Передавать vision-модели страницу и увеличенные спорные области.

Это повышает точность и снижает стоимость API.

## Модель данных

Пример кандидата размера:

```python
class DimensionCandidate(BaseModel):
    id: str
    value_mm: int
    text_bbox: tuple[float, float, float, float]
    role: Literal["main", "branch", "nested", "irrelevant", "ambiguous"]
    included: bool
    associated_edge_id: str | None
    confidence: float
    reason: str
```

Пример результата страницы:

```python
class PageResult(BaseModel):
    page_number: int
    line_id: str | None
    segments: list[DimensionCandidate]
    total_length_mm: int | None
    formula: str | None
    status: Literal["ok", "review", "error"]
    remarks: list[str]
```

Модель может предлагать связи, но не должна самостоятельно задавать итоговую сумму без проверки.

## Structured output

Каждый ответ модели должен:

- соответствовать JSON Schema;
- содержать координаты использованных объектов;
- содержать роль каждого размера;
- содержать причину включения или исключения;
- явно перечислять неоднозначные области;
- не содержать рассчитанное «на глаз» значение без списка участков.

Невалидный ответ:

1. сохраняется в журнале;
2. не используется в расчёте;
3. повторно запрашивается ограниченное число раз;
4. после исчерпания попыток переводит страницу в `review` или `error`.

## Проверка уверенности

Нельзя использовать только значение `confidence`, придуманное LLM.

Итоговая уверенность должна учитывать наблюдаемые признаки:

- PDF-текст и OCR совпали;
- рядом найдена размерная линия;
- найдены обе выносные линии;
- размер привязан ровно к одному ребру;
- геометрический алгоритм и LLM согласны;
- диапазон не дублирует уже учтённый участок;
- координаты точек подключения не противоречат результату;
- повторная проверка дала тот же ответ.

При недостатке подтверждений:

```text
status = review
total_length_mm = null
remarks = ["Размер 1788 может относиться к двум соседним участкам"]
```

## Визуальная разметка

Рекомендуемая цветовая схема:

- зелёный — учтённый размер основной трассы;
- оранжевый — учтённое ответвление;
- фиолетовый — исключённый вложенный размер;
- красный — неоднозначный участок;
- серый — распознанный, но не относящийся к длине объект.

Каждый учтённый размер получает метку `L1`, `L2`, `L3` и так далее. Формула в таблице должна использовать те же метки.

## Формат результатов

```text
results/
├── results.xlsx
├── results.csv
├── annotated.pdf
├── metrics.json
└── pages/
    ├── page_01.json
    ├── page_02.json
    └── ...
```

Таблица должна содержать:

| Поле | Содержание |
|---|---|
| page_number | Номер листа |
| line_id | Обозначение линии |
| length_mm | Длина в миллиметрах |
| length_m | Длина в метрах |
| formula | Формула по меткам или значениям |
| status | `ok`, `review` или `error` |
| remarks | Ошибки и неоднозначности |

## Метрики API

Для каждого обращения к модели необходимо сохранять:

```text
job_id
page_number
model
purpose
input_tokens
output_tokens
elapsed_seconds
estimated_cost_usd
retry_number
```

Итоговый отчёт должен показывать:

- общее время обработки;
- среднее время на страницу;
- количество обращений к ИИ;
- среднее количество обращений на страницу;
- стоимость каждой страницы;
- общую стоимость;
- число повторных обращений.

## Хранение в базе

Минимальные сущности:

- `processing_job` — запуск обработки файла;
- `page_result` — результат одной страницы;
- `model_call` — отдельный вызов модели и его метрики.

Сырые изображения и PDF лучше хранить в файловой системе или объектном хранилище, а в базе сохранять пути и метаданные.

## Этапы самостоятельной разработки

### Этап 0. Ручной эталон

До написания основной системы вручную разобрать:

1. учебный пример;
2. первый лист;
3. один сложный лист с ответвлениями;
4. остальные семь листов.

Для каждого размера сохранить:

- значение;
- координаты;
- включён или исключён;
- основная трасса или ветвь;
- связанный участок;
- причину исключения;
- ожидаемую итоговую формулу.

Результат — `ground_truth.json`. Это основа eval-набора.

### Этап 1. PDF Inspector

Первая программа ещё не рассчитывает длину. Она должна:

- открыть PDF;
- вывести размеры страниц;
- извлечь текстовые блоки с координатами;
- найти числовые кандидаты;
- нарисовать рамки вокруг кандидатов;
- сохранить диагностические изображения и JSON.

**Критерий готовности:** видно, какие размеры удаётся получить без OCR.

### Этап 2. OCR fallback

- определить пропущенные или подозрительные области;
- вырезать увеличенные фрагменты;
- применить OCR только к ним;
- привести координаты кропа обратно к координатам PDF;
- объединить результаты без дубликатов.

**Критерий готовности:** числовые размеры учебного примера обнаруживаются вместе с координатами.

### Этап 3. Первый вызов vision-модели

Передать модели:

- изображение страницы;
- список числовых кандидатов;
- координаты кандидатов;
- правила включения и исключения;
- строгую схему ответа.

**Критерий готовности:** учебный пример возвращает правильные роли для `60`, `1950`, `650`, `840`, `522`, `250`, `34`, `916` и `300`.

### Этап 4. Граф и детерминированные проверки

- реализовать узлы и рёбра;
- привязать размеры к рёбрам;
- определить дубликаты;
- исключить вложенные размеры;
- выполнить суммирование;
- сформировать воспроизводимую формулу.

**Критерий готовности:** тест учебного примера стабильно получает `4306 мм` без сложения внутри LLM.

### Этап 5. Обработка 10 листов

- запустить единый алгоритм без условий по номеру страницы;
- разобрать ошибки;
- расширять общие правила, а не добавлять исключения под конкретные листы;
- отмечать неоднозначные листы как `review`.

**Критерий готовности:** все 10 листов имеют результат либо обоснованный статус проверки.

### Этап 6. Отчёты и разметка

- CSV;
- XLSX;
- JSON по каждой странице;
- размеченный PDF;
- отчёт по времени и стоимости.

### Этап 7. CLI, API и Docker

- CLI запускает обработку файла;
- FastAPI использует то же ядро;
- Docker собирается с нуля;
- секреты передаются только через переменные окружения;
- `.env` не попадает в Git.

### Этап 8. Финальная проверка

- запуск по инструкции на чистом окружении;
- тесты без реального API через mock-клиент;
- хотя бы один интеграционный тест с моделью;
- повторная обработка даёт сопоставимый результат;
- в репозитории отсутствуют ключи и временные файлы;
- README соответствует фактическому поведению программы.

## Evals и тестирование

### Unit-тесты

Проверяют:

- сложение участков;
- исключение дубликатов;
- вложенные интервалы;
- преобразование миллиметров в метры;
- формирование формулы;
- переходы между статусами;
- расчёт стоимости.

### Интеграционные тесты

Проверяют:

- извлечение текста из PDF;
- аннотирование PDF;
- создание XLSX;
- валидацию ответа LLM;
- работу API и базы.

### Eval-набор

Минимальные метрики:

- точность распознавания чисел;
- точность классификации `included/excluded`;
- точность привязки к участкам;
- абсолютная ошибка итоговой длины;
- количество полностью правильно рассчитанных листов;
- количество листов `review`;
- количество ложных уверенных результатов;
- стоимость и время на страницу.

Самая важная метрика — число полностью правильных листов при отсутствии неподтверждённых результатов со статусом `ok`.

## Отказоустойчивость

Нужно предусмотреть:

- таймаут API;
- ограниченные повторы с backoff;
- невалидный JSON;
- частично распознанную страницу;
- отсутствие текстового слоя;
- повреждённый PDF;
- временную недоступность модели;
- повторный запуск без потери уже готовых страниц;
- идемпотентность создания отчётов.

## Что сознательно не используется

### RAG и embeddings

RAG не решает основную задачу, поскольку требуется пространственная интерпретация конкретного чертежа, а не поиск информации в коллекции документов.

### MCP

MCP может стать будущим интерфейсом подключения сервиса к внутренним инструментам компании, но для тестового задания не является необходимым.

### Обучение собственной модели

Десяти листов недостаточно для полноценного обучения. Гораздо важнее качественная архитектура, eval-набор и проверяемый pipeline.

### Микросервисы и Kubernetes

Для тестового задания это неоправданное усложнение. Достаточно модульного приложения и одного контейнера.

## Чего делать нельзя

- Просить модель сразу вернуть единственную сумму.
- Складывать все числа, похожие на размеры.
- Добавлять условия по номеру страницы.
- Зашивать координаты конкретных листов.
- Использовать OCR как единственный источник данных.
- Считать заявленную моделью уверенность доказательством.
- Исправлять результаты вручную без фиксации этого факта.
- Тратить основное время на красивый интерфейс до появления корректного ядра.
- Добавлять технологии из вакансии только ради упоминания.
- Скрывать ошибочные листы вместо статуса `review`.

## Критерии сильной итоговой работы

- Один алгоритм работает на всех листах.
- Итоговая арифметика выполняется кодом.
- Каждый учтённый размер виден на разметке.
- Каждое исключение имеет объяснение.
- Неоднозначные результаты не выдаются как подтверждённые.
- Промежуточные данные сохраняются в JSON.
- Стоимость вычисляется по фактическому использованию API.
- Есть eval-набор и автоматические тесты.
- CLI и FastAPI используют одно ядро.
- Проект запускается по README на чистом окружении.
- Docker-образ собирается без ручной настройки.
- В репозитории нет API-ключей и специальных исправлений для отдельных страниц.

## Ближайший шаг

Создать минимальный проект и написать `inspect_pdf.py`, который:

1. Открывает первый лист исходного PDF.
2. Извлекает текстовые блоки с координатами.
3. Выбирает блоки, содержащие числовые значения.
4. Рисует вокруг них рамки.
5. Сохраняет диагностический PNG и JSON.

На этом этапе не нужно подключать LLM, OCR, FastAPI или базу данных. Сначала следует измерить, сколько полезной информации можно получить непосредственно из PDF.
